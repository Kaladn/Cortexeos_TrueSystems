Yep. Now we can state the build cleanly. The old HTML proves the tiny local intake/mapping pattern; the plugin runner proves the detached lab pattern; the current TrueSystems laws tell us where authority lives. The missing piece is to weld those into TruePlug’s contained dataset-and-plugin factory without dragging the old fake “semantic” scoring forward.

The core idea is:

TruePlug gets its own disposable mini-system, creates or ingests data inside that boundary, maps exact positions and relationships, calculates recurrence-based weights over the whole contained document/dataset, builds Top-K traversal candidates, lets ARC/assembler experiment over that structure, and only exports a candidate plugin + qualification packet. It never needs canonical TrueSystems data.

The old mapper already has the correct mechanical skeleton: local file intake, positional objects, context windows, per-object relationship arrays, metadata-rich exports, and fully local browser execution. The larger version already supports multi-file intake, adjustable relationship depth, combined dataset generation, and JSON/CSV/JSONL export.

What we throw away is the bullshit semantic labeling and arbitrary heuristics. That larger file literally derives “similarity” from character overlap/length/substring and has a placeholder frequency weight. The modern weight is measured occurrence geometry.

Nothing outside that root is visible unless a separately defined development fixture explicitly exposes it.

That hardens what the old plugin runner already does well: detached discovery, mounting, fixtures, mock services, health/route inspection, and promotion preparation.

The current runner is detached but not sandboxed because plugins share its process/runtime, so this build adds per-plugin process, environment, filesystem, network, resource and termination boundaries.

2. Intake law

Do not begin with “semantic meaning.”

Begin with exact observed structure.

For ordered text:

dataset
→ document
→ paragraph
→ sentence
→ exact occurrence

Every occurrence keeps:

dataset_id
document_id
container_id
occurrence_id
exact_text
ordinal
byte/span coordinates
parent chain
source hash

No stemming. No synonym merging. No silent normalization. No semantic collapse.

That preserves the current TrueSystems law that source remains authority and graphs carry addresses/measurements rather than replacing source.

3. Relationship field

For ordered material, each exact occurrence can expose a signed local field:

... -3 -2 -1 | CENTER | +1 +2 +3 ...

The radius is configurable.

6-1-6 remains a useful default experiment for ordered data, not a universal geometry.

For every observed pair:

(center_occurrence, neighbor_occurrence)

record:

signed_offset
absolute_offset
same_sentence
same_paragraph
same_document
same_dataset
center_identity
neighbor_identity
witness_location

No inferred edge merely because two strings look similar.

4. The weight you’re talking about

This is the key correction.

Weight is not an arbitrary decimal assigned to a word.

Weight comes from the measured question:

How often did object B occur at a particular positional relationship to object A across the admitted container?

So for focused object A, maintain counts:

A → B @ -6 = count
A → B @ -5 = count
...
A → B @ -2 = count
A → B @ -1 = count
A → B @ +1 = count
A → B @ +2 = count
...

Your example:

How many times did buildout occur two positions away?

is literally one channel:

count(center=A, neighbor="buildout", offset=±2)

But we preserve the sign too:

A → buildout @ -2 = 17
A → buildout @ +2 = 41

because direction may matter.

Then aggregate without destroying the raw counts:

offset_count[-2] = 17
offset_count[+2] = 41
absolute_distance_count[2] = 58

That gives us several independent measured channels.

5. Full-document weight

Now zoom out.

For a focused relationship A → B, full-document weight is built from all exact witnesses in that document, not merely the current local window.

At minimum preserve:

pair_occurrence_count
distinct_A_occurrences
distinct_B_occurrences
signed_offset_histogram
absolute_distance_histogram
same_sentence_count
same_paragraph_count
document_count

Then derive useful projections.

For example:

pair_mass(A,B)
    = total exact witnessed A↔B positional co-occurrences

and:

offset_mass(A,B,d)
    = witnesses of B at signed offset d from A

You can also calculate recurrence coverage:

A_coverage(A,B)
    = distinct A occurrences that witness B
      ------------------------------------
      total distinct A occurrences

That answers:

When A appears, how consistently does B participate in A’s field?

That is a useful deterministic measurement.

It is not probability of truth.

6. Positional pressure

Raw counts stay raw.

For traversal ranking, you can create a separate positional pressure channel.

The current system already has a clean rational form proposed for bounded structural traversal:

pressure(distance) = (N - distance + 1) / N

while retaining raw distance, radius, numerator, denominator, direction and axis.

For a radius of 6:

distance 1 → 6/6
distance 2 → 5/6
distance 3 → 4/6
distance 4 → 3/6
distance 5 → 2/6
distance 6 → 1/6

So if buildout occurred 41 times at +2, its pressure-weighted positional mass for that lane is:

41 × 5/6

But keep both values:

raw_count = 41
pressure = 5/6
weighted_mass = 205/6

Never only save the final decimal.

That means every ranking is reproducible.

7. Top-K

Now we get the lovely part you remembered.

For focused object A, build candidates from observed neighbors.

Each candidate B can have a ranking vector like:

B:
  pair_count
  distinct_center_coverage
  signed_position_counts
  nearest_distance
  weighted_positional_mass
  sentence_support
  paragraph_support
  document_support

Then Top-K selection can remain deterministic.

A simple first ordering could be:

1. highest distinct-center coverage
2. highest total witnessed pair count
3. highest positional weighted mass
4. nearest minimum observed distance
5. canonical first source ordinal

Or, if you want the old lane idea preserved, select Top-K per signed lane:

-6 → top K
-5 → top K
...
-1 → top K
+1 → top K
...
+6 → top K

That is actually nicer because one dominant relationship cannot erase everything else.

Then you can produce:

focus = A

-2:
  buildout  count=17
  worker    count=14
  graph     count=11

+2:
  buildout  count=41
  plugin    count=28
  test      count=19

Now ARC or the assembler has a very small, structured candidate surface to walk.

8. Parent/container weight

And we should preserve the other thing you’ve been describing lately: the child relationships can boil upward.

Example:

paragraph P
├── A ↔ buildout
├── A ↔ plugin
├── A ↔ graph
└── A ↔ test

The paragraph gets a parent summary derived from those child observations.

Likewise:

document
→ paragraphs
→ sentences
→ occurrences

The document-level surface can say:

A ↔ buildout:
  child_witness_count = 58
  paragraphs_witnessed = 9
  sentences_witnessed = 22
  dominant_offsets = [+2, -2]

But the parent score never replaces the children.

Click/open/drill into the children for proof.

That’s the useful mini-graph-inside-the-larger-graph idea you were describing earlier.

9. Relationship decay and takeover

This also gives us the proper place for your relationship decay/takeover mechanism.

Important distinction:

The historical relationship does not vanish.

What can decay is the current traversal pressure or relevance to the active focus.

So as the walk proceeds:

A → B → C → D

A’s influence can decline while a newly witnessed C→X relationship overtakes it.

Keep channels separate:

historical_count
current_focus_pressure
path_hops
current_parent

Then another candidate can overtake because it has stronger witnessed structure at the new center.

That gives pseudo-reasoning without deleting historical relationships.

10. Multi-container containment

Never allow positional relationships to casually jump across unrelated containers.

Sentence relationships stay in sentence bounds.

Paragraph relationships stay in paragraph bounds.

Document relationships stay in document bounds.

Dataset/cross-document relationships require their own explicit channel.

This is critical because the newer relationship experiments already showed that unconstrained walking can manufacture cross-container edges that should not exist. The current governing laws explicitly say text clouds obey block/document containment and naturally contract at edges.

16. Promotion boundary

This remains hard:

TruePlug:
"This candidate passed my contained development contract."

TrueCore:
"This candidate is admitted with these exact authorities."

TruePlug does not self-register.

And do not reuse the old passed >= 6 style promotion logic. The runner currently has a structural readiness weakness where any six passing checks may produce “ready.”

Use mandatory gates:

SOURCE_HASHED
SANDBOX_CONTAINED
MANIFEST_VALID
ENTRYPOINT_LOADS
TESTS_PASS
EFFECTS_WITNESSED
PERMISSIONS_DECLARED
NETWORK_CONTAINED

FAILURE_BEHAVIOR_WITNESSED
NO_CRITICAL_UNRESOLVED
PACKAGE_IMMUTABLE

All required.
